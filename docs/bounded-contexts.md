# Межі контекстів Event Platform

## Предметна область

Платформа допомагає організаторам створювати та публікувати заходи, а відвідувачам — знаходити події, бронювати місця, оплачувати квитки та залишати відгуки. Контролери перевіряють видані квитки на вході; кожен сервіс відповідає за власний життєвий цикл даних.

## Власники даних і агрегати

| Контекст | Агрегати та корені | Життєвий цикл |
|---|---|---|
| Event Catalog | `Organizer`; `Category`; `Event` (корінь) + `EventVenue` (1:1) + `EventTag` (зв’язок із тегом) | Організатор створює чернетку, редагує її, публікує, завершує або скасовує. Видалення події — м’яке. Категорії та теги є довідниками. |
| Ticketing | `TicketType`; `Reservation` (корінь) + `ReservationDetails` (1:1) + `ReservationItems` (склад бронювання); `Ticket` (видається для одиниці квитка) | Тип квитка задає ціну та місткість. Бронювання утримує квитки до завершення оплати/терміну дії. Підтвердження оплати змінює бронювання і видає квитки; сканування змінює статус квитка. |
| Payments & Feedback | `Payment`; `Notification`; `Review` (корінь із вбудованим автором і невеликими коментарями); `Discussion` (окремий документ повідомлення) | Платіж проходить власний платіжний статус і не є джерелом статусу бронювання. Відгук створюється після перевірки квитка; довгі обговорення ростуть як окремі документи. |

## Правила інтеграції

- Кожна таблиця/колекція має одного власника-контекст.
- Між базами немає SQL foreign keys. UUID `EventPublicId`, `ReservationPublicId`, `TicketPublicId`, `UserPublicId` — зовнішні ідентифікатори; їх валідність перевіряється інтеграційними подіями/API.
- Поточні дані каталогу можуть оновлювати локальну проєкцію Ticketing через події інтеграції; історичні знімки в бронюваннях, платежах і відгуках не переписуються.
- Обробники інтеграційних подій мають бути ідемпотентними за event ID/версією. Для узгодженості доставки рекомендується transactional outbox у власнику даних; окрема інфраструктура брокера повідомлень до складу схеми не входить.
- Обидві реляційні БД використовують PostgreSQL. Локальні ключі — `BIGINT GENERATED ALWAYS AS IDENTITY`; міжсервісні ідентифікатори — UUID. Для конкурентних змін SQL-сутності мають прикладний `version`-токен; клієнт оновлює рядок умовно за очікуваною версією та збільшує токен.

Детальна таблиця полів-знімків, власників і політик оновлення знаходиться в кореневому [README](../README.md#політика-копіювання-даних).
